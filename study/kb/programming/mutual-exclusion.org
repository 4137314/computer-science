#+title: Atomics and mutual exclusion
#+summary: A data race is removed either by making the operation indivisible (=std::atomic=) or by enclosing the accesses in a critical section protected by a =std::mutex=, preferably locked through the RAII guard =std::lock_guard= so that it is released on every exit path.

* Method
- *Atomic variables* (=<atomic>=): =std::atomic<int> counter;= makes =++counter=, =fetch_add=, =load=, =store= indivisible. Good for single variables.
- *Mutex* (=<mutex>=): =m.lock()= enters the critical section, waiting if another thread is inside; =m.unlock()= leaves it. At most one thread runs the section at a time.
- =std::lock_guard<std::mutex> g(m);= locks in the constructor and unlocks in the destructor: the mutex is released even when an exception leaves the block.
- =std::recursive_mutex= can be locked again by the thread that holds it (nested functions locking the same mutex).
- =std::lock(m1, m2)= (or =std::scoped_lock g(m1, m2);=) acquires several mutexes without deadlock.

* Example
#+begin_src c++
  std::mutex m;
  long total = 0;
  void add(long x) {
    std::lock_guard<std::mutex> g(m);   // critical section starts
    total += x;
  }                                     // and ends here, always
#+end_src

* Intuition
A mutex is the key of a single bathroom: whoever holds it is alone inside. The guard is a door that locks behind you and unlocks when you leave, however you leave.

* Pitfall
Locks only work if every access takes them: one unprotected read reintroduces the race. Holding a lock while calling unknown code invites [[id:deadlock-starvation][deadlock]].
